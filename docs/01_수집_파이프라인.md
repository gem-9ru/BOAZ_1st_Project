# 수집 파이프라인

원본 사이트에서 최종 부산 CSV까지, 데이터가 거치는 전 과정입니다.

```
수집 전
 ①  정책 감사         수집해도 되는 사이트인지 판정
 ②  정본 총건수 확보    사이트가 밝힌 "전체 N건"을 먼저 확보
 ③  지역 접근 경로 확인  지역이 목적이면 사이트의 지역 필터를 쓴다

수집
 ④  목록 수집         src/{사이트}.py          data/{사이트}.csv        240,608행
 ⑤  상세 보강         src/duty_detail.py       data/{사이트}_상세.csv    39,671행
 ⑥  수집 검증         audit/coverage_check.py  정본 대비 98% 이상인지

가공
 ⑦  정규화           pipeline/normalize.py     build/공고_정규화.csv     227,215행
 ⑧  중복 병합         pipeline/dedup.py         build/공고_통합.csv      161,403건
 ⑨  부산 추출         pipeline/extract_busan.py 부산/                    25,276건
```

각 단계의 "왜" 는 대부분 한 번 크게 틀렸던 경험에서 나왔습니다.
그 사례를 함께 적어 두었으니, 새 사이트를 추가할 때 같은 함정을 피하는 데 쓰면 됩니다.

---

## ① 정책 감사

수집 **전에** 세 층을 확인합니다. 셋 중 하나라도 금지면 수집하지 않습니다.

| 층 | 확인 대상 | 구속 범위 |
|---|---|---|
| 1 | `robots.txt` | 크롤러 일반 |
| 2 | 페이지 본문·푸터 고지 | 비회원 포함 |
| 3 | 이용약관 회원 의무 | 계정 보유자 |

2층은 **반드시 렌더링된 페이지**에서 확인합니다. 푸터가 클라이언트 렌더링이면
`requests` + BeautifulSoup 으로는 보이지 않습니다.

3층 때문에 **계정을 만들면 오히려 제약이 늘어납니다.** "서비스로 얻은 정보의 복제 금지"
같은 조항이 계약상 구속력을 갖기 때문입니다.

→ 상세: [03_정책감사.md](03_정책감사.md)

## ② 정본 총건수 확보

수집을 시작하기 전에 **사이트가 밝힌 전체 건수**를 먼저 찾아 기록합니다.
이 숫자가 없으면 "다 받았다"를 검증할 방법이 없습니다.

찾는 곳은 네 가지입니다.

- 목록 화면의 "전체 N건" 표기
- API 응답의 `total_count` / `totalCount` / `intTotalRecordCount`
- sitemap 의 URL 개수
- 마지막 페이지 번호 이분 탐색 × 페이지당 건수

## ③ 지역이 목적이면 지역 필터를 직접 쓴다

이 데이터셋의 목적은 부산입니다. 그런데 처음에는 전국을 받아 부산을 걸러냈고,
그게 틀렸습니다.

```
실제 공고   "서울, 경기, 대구, 경북, 부산, 경남"
JSON-LD    jobLocation 주소 1개만 → "서울 중구"
결과       부산 집계에서 탈락
```

| 사이트 | 전국 수집 후 필터 | 지역 필터 직접 |
|---|---:|---:|
| 잡코리아 | 4,149 | **8,660** |
| 커리어 | 852 | **5,209** |
| 널스케이프 | 0 | **49** |

**파라미터를 보냈다고 필터가 걸리는 게 아닙니다.** 점핏·나라일터·건설워커는
지역 파라미터를 받아도 전국 결과를 돌려줍니다. 건수가 실제로 줄어드는지 확인해야 합니다.
그런 사이트는 전국 전수 후 필터링밖에 방법이 없습니다.

→ 사이트별 경로와 정본 대조: [08_부산_전수조사.md](08_부산_전수조사.md)

## ④ 목록 수집

사이트마다 데이터를 꺼내는 경로가 다릅니다. 우선순위는 아래 순입니다.

| 경로 | 사이트 | 장점 |
|---|---|---|
| 공개 REST API | 원티드, 점핏, 캐치, 자소설닷컴, 잡플래닛 | 필드가 구조화돼 있음 |
| sitemap + 상세 JSON-LD | 잡코리아, 리멤버커리어 | 전수 보장 |
| Next.js `__NEXT_DATA__` | 링커리어 | SSR 상태를 그대로 파싱 |
| 목록 HTML 파싱 | 부산일자리정보망, 커리어, 나라일터, 잡알리오 | 그 외 |
| 목록 → 상세 meta/JSON-LD | 게임잡, 건설워커, 미디어잡 | 목록에 없는 필드 보강 |

**공통 처리 — `src/common.py`**

- `RateLimiter` : 전역 요청 간격 제어. 사이트별 `delay` 지정
- 체크포인트 : 수집분을 `logs/{사이트}.ckpt.jsonl` 에 append.
  중단해도 재실행하면 이어서 진행합니다
- `parse_jobposting_ld()` : JSON-LD `JobPosting` 스키마 파서.
  `occupationalCategory`(직무), `validThrough`(마감), `experienceRequirements`(경력) 추출
- 세션 재사용, 재시도, 실패 URL 기록

### 목록 캡 우회

서버가 결과를 잘라내는 사이트가 있습니다(목록 100건, 딥페이지네이션 1만건 상한 등).
이럴 때는 **지역 × 직무로 조건을 쪼개** 각 슬라이스를 캡 아래로 내린 뒤 합칩니다.
커리어는 이 방식으로 100건 → 11,862건이 됐습니다.

> 단, 슬라이스에 **자기가 정한 상한**을 걸면 안 됩니다.
> 커리어에 `MAX_PAGE=12`(600건)를 걸어둬서 부산이 852건에서 잘렸습니다.
> 실측해보니 지역 슬라이스는 100페이지까지 정상 동작했습니다(5,209건).

## ⑤ 상세 보강 — `src/duty_detail.py`

**목록과 상세는 역할이 다릅니다.**

| 단계 | 목적 | 얻는 것 |
|---|---|---|
| 목록 | 빠짐없이 **찾아낸다** | 공고 ID, 직무 태그, 학력, 지역, 경력, 마감일 |
| 상세 | **깊이** | 담당업무, 자격요건, 우대사항, 모집분야, 직종, 업종, 근무시간, 모집인원 |

목록에 직무 태그가 있다고 상세를 건너뛰면 안 됩니다.
**담당업무·자격요건·모집인원은 상세에만 있습니다.**

사이트마다 상세 구조가 달라 전용 파서를 둡니다.

| 파서 | 대상 | 특징 |
|---|---|---|
| `p_saramin_detail` | 사람인 | `/relay/view-detail` (9KB). `popup`(431KB)과 같은 내용 |
| `p_jobkorea` | 잡코리아 자체 | React `RecruitmentItem` 블록 + **상세요강 iframe** |
| `p_jobkorea_ext` | 잡코리아 워크넷 연계 | 레이아웃이 완전히 다름 |
| `p_wanted` | 원티드 | API `detail.main_tasks` |
| `p_career` | 커리어 | 상세요강이 base64 이미지. `관련 키워드` 만 건짐 |
| `p_text` | 그 외 | 라벨 기반 본문 절편 추출 |

**차단 감지** — 연속 실패 60건이면 중단합니다.
사람인에서 IP 차단을 당했을 때 워커 4개가 전부 물려 6분간 조용히 서 있었습니다.
프로세스는 살아 있고 로그도 멈춰만 있어 진행 중처럼 보였습니다.

## ⑥ 수집 검증

`src/audit/coverage_check.py` 가 사이트별 정본 총건수를 다시 조회해 수집분과 대조합니다.
17개 사이트에 대한 개별 조회 함수가 들어 있습니다.

통과 기준과 위험 신호:

- [ ] 수집 건수 / 정본 건수 ≥ **98%**
- [ ] 건수가 코드에 박아둔 상한과 **정확히 일치하지 않을 것** (예: 800 = 80페이지 × 10)
- [ ] 신규 0건으로 끝난 메뉴가 없을 것
- [ ] 고유 ID 개수 == 행 수 (쿼리스트링만 다른 같은 공고 방지)

→ 상세: [04_수집검증.md](04_수집검증.md)

## ⑦ 정규화 — `pipeline/normalize.py`

사이트마다 다른 스키마를 하나로 합치고, 네 가지 일을 합니다.

### 7-1. 스키마 통일

18개 사이트의 컬럼을 공통 스키마로 매핑합니다.
지역 문자열은 `시도` / `시군구` / `지역원문` 으로 분해하고,
`시군구 → 시도` 역매핑 표를 둬서 "해운대구"만 있어도 시도를 부산으로 채웁니다.

### 7-2. 알바 공고 제외 — 4,235행

알바는 대상이 아닙니다. 단순 키워드 매칭이 아니라 **어디에서 매칭됐는지**로 판정합니다.

| 매칭 위치 | 판정 |
|---|---|
| 공고제목 | 제외 |
| 고용형태 칸만 | 정규/계약/인턴이 함께 있으면 유지 |
| 직무 설명문만 | 유지 |

재노출 사이트가 밝힌 **원출처가 알바 사이트**면 고용형태 표기와 무관하게 제외합니다.
잡코리아 부산 목록에는 알바몬 링크가 469건 섞여 옵니다.

"아르바이트생 관리" 같은 정규직 공고가 제목이 아닌 본문에서 걸리는 것을 막기 위한 구분입니다.

### 7-3. 마감 공고 제외 — 9,158행

`SNAPSHOT = "2026-09-07"` 보다 마감일이 앞서면 버립니다.
"상시채용" / "채용시 마감" 처럼 날짜가 없는 것은 유지합니다.

### 7-4. 상세 보강 데이터 합류

`pipeline/detail_join.py` 가 `data/*_상세.csv` · `data/*_직무상세.csv` 를
`공고URL` 로 붙입니다. 이 파일들은 공고 목록이 아니라 조인 테이블이라
사이트 순회에서 제외됩니다(안 그러면 건수가 두 배로 부풉니다).

목록에 없던 고용형태·근무지역도 상세 값으로 채웁니다.

### 7-5. 직무 보강

직무 칸이 비었거나 "기업채용" 같은 분류명뿐인 공고가 많습니다. 출처를 6단계로 씁니다.

| 순위 | 출처 | 처리 |
|---|---|---|
| 1 | `직종` (표준 직업분류명) | 사이트가 분류한 값 — 그대로 신뢰 |
| 2 | `직무키워드` (사이트 직무 코드) | 〃 |
| 3 | `모집분야` | 어휘 사전으로 거름 |
| 4 | 원본 직무 칸 | 〃 |
| 5 | 공고제목 | 〃 |
| 6 | `담당업무` 첫 문장 | 〃 |

제목에서만 뽑던 방식은 "2026년 신입사원 공개채용" 에서 아무것도 못 건졌습니다.

어휘 사전 외에 쓰는 패턴:

| 방법 | 예 |
|---|---|
| 직무 어휘 사전 (약 350개) | "간호조무사", "백엔드", "요양보호사" |
| 직함 어미 패턴 | ...반장 / 팀장 / 기사 / 관리사 / 조리사 / 치료사 |
| 존칭 패턴 | "피부관리사**님**" |
| 부서·병동 패턴 | 원무과 / 외래 / 병동 / 수술실 |

추출한 토큰은 회사명과 겹치거나, 숫자·비직무 라벨이면 버립니다.
괄호가 짝이 안 맞으면 복구합니다.

> **한국어 정규식 주의**
> `(?<![가-힣])` 같은 단어경계 룩비하인드를 쓰면 안 됩니다.
> 한국어는 조사·수식어가 공백 없이 이어져서("피부과에서 피부관리사님을")
> 앞 글자가 거의 항상 한글이라 매칭이 사실상 사라집니다.

## ⑧ 중복 병합 — `pipeline/dedup.py`

같은 공고가 여러 사이트에 올라옵니다. Union-Find 로 묶어 하나의 `통합키`를 부여합니다.
3단계를 순서대로 적용하며, 뒤 단계일수록 보수적입니다.

| 단계 | 근거 | 병합 |
|---|---|---:|
| 1 | 외부원본ID 일치 (사이트가 밝힌 원본 출처) | 0쌍 |
| 2 | 회사키 + 제목키 완전일치 | 56,781쌍 |
| 3 | 회사키 동일 + 제목 유사도 | 8,647쌍 |

**회사키** — 법인격 표기를 제거해 정규화합니다. `(주)`, `㈜`, `주식회사`, `유한회사` 등.
공백 변형(`CJ 생수` vs `CJ생수`)도 함께 흡수합니다.

**3단계 근무형태 가드** — 회사·직무가 같아도 아래 어휘가 서로 다르면 병합하지 않습니다.

```
야간 주간 심야 오전 오후 저녁 새벽 주말 평일 교대 2교대 3교대 격일
상근 전담 야간전담 당직 재택 파견 출장 상주 순회 단기 장기 주5일 주6일 ...
```

같은 병원의 "야간전담 간호사"와 "주간 간호사"는 **다른 공고**이기 때문입니다.

**회귀 테스트** — `pipeline/test_relation.py` 18케이스. 로직 수정 시 반드시 통과해야 합니다.

**병합이 결손을 메웁니다.** 사이트마다 채워지는 필드가 달라서(사람인 담당업무 91%,
잡코리아 근무시간·급여) 같은 공고를 여러 곳에서 받으면 값이 있는 쪽을 고릅니다.
상세 컬럼 14개가 통합 결과에 그대로 실립니다.

결과: 227,215행 → **161,403건** (65,428행 병합, 28.8%).
2개 이상 사이트에 동시 게재된 공고는 20,925건입니다.

## ⑨ 부산 추출 — `pipeline/extract_busan.py`

판정을 **강 / 중 / 약** 세 등급으로 나눕니다. 분석할 때 "강만" 또는 "강+중" 을
고를 수 있게 하기 위해서입니다.

| 판정근거 | 확실도 | 건수 |
|---|---|---:|
| 상세 **근무지주소**에 부산 | 강 | 9,840 |
| `시도` = 부산 (단일지역) | 강 | 43,486 |
| 부산 소속 시군구인데 시도가 빈 값 | 강 | — |
| `지역원문` 에 부산 포함 (단일) | 강 | 58 |
| 다지역 공고에 부산 포함 | 중 | 3,075 |
| 부산일자리정보망인데 지역 미상 | 중 | 657 |
| 공고제목에 부산 지명 (주소 없음) | 약 | 240 |
| 제목엔 부산이나 **근무지주소는 타지역** | 보류 | 별도 파일 |

**근무지주소를 정본으로 봅니다.** 다지역 공고를 넣는 건 맞지만
"정말 부산에서 뽑는가" 는 따로 확인해야 합니다. 지역 태그가 넓게 붙었을 뿐
실제 근무지는 서울인 공고를 넣으면 부산 수요가 부풀려집니다.

근거는 실측입니다.

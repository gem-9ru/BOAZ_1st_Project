# 3. 버려지고 있던 값을 회수했습니다

레포의 문서·코드를 하나씩 대조하다 **상세페이지에서 이미 받아 둔 값이 최종
데이터까지 오지 못하고 있는 것**을 찾았습니다. 재수집 없이 회수했습니다.

| 무엇 | 어디에 있었나 | 채움률 |
|---|---|---|
| **급여** | 부산일자리정보망은 급여를 `임금조건` 칸에 담는데 매핑 테이블에 그 키가 없었습니다. 22,694건이 통째로 버려지고 있었습니다 | **33% → 83%** (금액이 든 건 22% → 40%) |
| **학력** | 부산일자리정보망은 학력을 `경력학력조건` 칸에 담습니다. `_경력학력` 로 실어 놓고 아무도 쓰지 않았습니다 | **72% → 91%** |
| 회사명 | 목록에 회사명이 없는 공고는 상세의 `기관명` 을 씁니다 | 92.9% → 93.2% |

`임금조건` 은 라벨이 한 번 더 붙어 옵니다 — `연봉 시급 10,320원`. 앞의 `연봉` 은
칸 제목이라 떼야 합니다. 그대로 쓰면 시급 10,320원이 '연봉 1만원' 으로 읽힙니다.

`detail_join.py` 의 docstring 에는 "얻는 것은 … 임금조건 … 이다" 라고 적혀
있었습니다. 의도는 있었고 매핑만 빠져 있었습니다.

# 4. 고친 버그 3개

정제하면서 **원본층에도 소급 적용**했습니다 (`src/pipeline/repair_fields.py`).

## 급여 범위의 하한이 날아가고 있었습니다 — 1,868건

```
"연봉 5,027~7,078만원"   →   급여최소 7078 · 급여최대 (빈칸)      ← 잘못
                        →   급여최소 5027 · 급여최대 7078       ← 고침
```

금액 정규식이 숫자 **뒤에** 단위를 요구해서, 단위가 뒤쪽 숫자에만 붙는 표기
(`5,027~7,078만원`)에서 앞 숫자를 놓쳤습니다. 상한값이 하한 칸에 들어가
급여 분석이 위로 편향되고 있었습니다.

## `관계없음` 이 경력 `기타` 로 빠지고 있었습니다 — 1,479건

`무관` 이 13,922 → 14,679건으로 늘었습니다. `기타` 는 카테고리 자체를 없앴습니다
— 경력 칸에 날짜·고용형태가 들어온 행(상위 파싱의 컬럼 밀림)이 집계에서 실제 값처럼
세어지고 있었습니다.

## 급여최소와 급여최대를 다른 사이트 행에서 따로 골라 왔습니다 — 122건

중복병합은 필드마다 값이 있는 행을 골라 결손을 메웁니다. 그런데 급여는 네 칸이
한 묶음인데 칸마다 따로 골라서 이런 값이 나왔습니다.

```
저장 "면접후결정 / 300만원 / (빈칸)"      원문 "면접후 결정"
저장 "시급 13000원 ~ 216"               원문 "시급 13000원 ~ 0원"
```

같은 문제를 코드가 채용인원에서는 이미 지적하고 처리해 뒀는데 급여·근무시간에는
적용이 안 돼 있었습니다. 네 칸을 **같은 행에서** 골라오도록 고쳤습니다
(급여 122건 · 근무시간 12건 → 0건).
